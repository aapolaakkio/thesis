\section{Experimental Settings}
\label{sec:experimental-settings}

In this section we go through the experiments performed to our pipeline. We describe the parameter values of each subproblem of our pipeline and the data used to test the pipeline. After this we go through the results from the performed experiments and discuss them briefly.

\subsection{Data}

The data used to test the pipeline is synthetic meaning it is randomly generated. We sample a per-graph scenario with a fixed graph id as the seed for the random number generator to ensure reproducibility. Each driver $k$ is drawn a shift start time $S_k\sim U(0, 60)$ and shift end time $H_k\sim U(240, 600)$ which together form the driver's shift window $[S_k, H_k]$, where both ends are drawn from a uniform distribution. Each customer $i$ is drawn a wanted pickup time $U_i\sim U(0, 600)$ and a ride duration $R_i\sim U(5, 30)$. A delay cap $E_{\max}=15$ bounds how much after a pickup may happen relative to the wanted pickup time of the customer. Minimum break length $B_{\min}=10$ and maximum break length $B_{\max}=60$ is used to ensure some time between rides, simulating needing to move to a different location for the next pickup. The customer pickup delays and driver idle time are given multipliers $D=1$ and $I=1$. A penalty $P=300$ is charged for every customer that ends up unassigned.

We configure the bipartite graphs to have 3-6 edges for each customer, meaning 3-6 preferences per customer. In addition, we allow at most 5 matched drivers for each customer. For drivers, the number of matched customers isn't capped, allowing all customers to be assigned to a single driver, theoretically.

In addition we set the time granularity $\Delta t=1$, meaning the scheduling is done at one minute precision, limit the resolve rounds to a maximum of 5 rounds and limit each Gurobi run to at most 30 seconds.

We run 18 scenarios and one reference scenario. The number of customers was set as $N\in\{6000,7000,8000\}$ and number of drivers as $K\in\{100,110,120,130,140,150\}$. We run a scenario for every customer and driver count pair $N \times K$. Additionally, we run one additional reference with $N=1000$ and $K=200$ to test the sensitivity of the pipeline.

We can see that the value of the maximum flow steadily increases when both the number of customers and the number of drivers increases. Increments in the number of the customers cause a larger increase in the maximum flow than the increments in the number of the drivers. We also see that the time it took to solve the matching also, on average, increases steadily when both the number of the customers and the number of the drivers increases.

The averages, however, behave a little differently. The average customers per driver increases when the number of the customers is increased but decreases when the number of the drivers is increased. This is logical as the drivers can match to a customer as long as there is an edge between them, and since the drivers have no limit to the number of matched customers, only the number of edges generated between the vertices limits the average. 

On the other hand, the drivers per customer is almost the same for all scenarios, averaging around $4.25$. This naturally happens due to the cap of maximum 5 drivers per customer and as there are always 3-6 edges per customer vertex, on average, customers are matched to $\frac{3+4+5+5}{4}=4.25$ drivers.

In every scenario the number of served customers is limited by the driver capacity, not by the matching done in the previous subproblem. A driver's shift is on average about 390 minutes long and a served ride occupies on average $17.5 + B_{\min} = 27.5$ minutes, so a driver can serve roughly 14--26 customers depending on the ride lengths. The observed maximum loads of 26--30 sit at the top of this range. Consequently, the number of assigned customers grows almost linearly in the number of drivers, by roughly 13 customers per added driver, while thousands of customers remain unassigned. Increasing the number of customers at a fixed driver count increases the assigned count only slightly. A larger number of customers gives each driver more short rides to choose from, which allows a denser packing of their shifts. Because every unassigned customer costs the penalty $P = 300$, the unassigned term dominates the objective; for example for $N = 6000$, $K = 100$ the penalty term accounts for about 98\,\% of the final objective value.

The scheduling runtime grows roughly linearly in the number of customers and shows no clear trend in the number of drivers (Figure~\ref{fig:sched-runtime}). This is expected, as the number of customers increases the size of each per-driver MILP, whereas an added driver only adds one more independent MILP of a similar size. All first-pass runtimes stay between 5 and 11 seconds, so the 30-second Gurobi time limit is never the binding factor.

The reference scenario with $N = 1000$ and $K = 200$ behaves differently. It is heavily over-provisioned as only 166 of the 200 drivers serve any customers and the average load is 4.1. Still, 326 customers remain unassigned. These customers cannot be served at all since a customer whose wanted pickup time falls late in the day fits inside the shift of only a small fraction of the drivers, and with on average 4.3 matched drivers per customer it is likely that none of them has a feasible start slot within the delay cap $E_{\max}$.

For all but the reference scenario, the iterated resolve improves the objective by 9--17\,\%. The improvement grows with the number of drivers at every customer count, for example from 12.0\,\% at $K = 100$ to 17.1\,\% at $K = 150$ for $N = 6000$. This is expected as the resolve improves the objective mainly by assigning previously unserved customers to drivers with spare capacity, each of which saves the penalty $P$, and a larger driver fleet has more spare capacity after the greedy pass. At a fixed number of drivers, the relative improvement decreases as the customer count grows, since the absolute gain stays similar while the objective itself grows with the number of unserved customers.

The resolve runtime grows with the number of customers and decreases with the number of drivers (Figure~\ref{fig:resolve-runtime}), and it is roughly 15 times the first-pass runtime, as each of the five driver orderings reruns per-driver MILPs over several rounds. The runtime stays below 200 seconds in all scenarios.

Figure~\ref{fig:resolve-boxplot} shows that the choice of the driver ordering matters little on average. The median excess over the per-scenario best ordering is below 0.11\,\% for every strategy, and no single ordering wins consistently, as can also be seen from the chosen-strategy column of Table~\ref{tab:resolve}. The ascending-conflicts ordering has the lowest median excess and the plain index ordering the largest spread.

  \centering

  \caption{Excess of each driver-ordering strategy's objective over the per-scenario best. Outliers are omitted for readability.}
  \label{fig:resolve-boxplot}

In the reference scenario the resolve worsens the objective by 10.7\,\%. Each re-solve is optimal for the driver being re-solved but not necessarily
for the whole driver fleet. A re-solved driver may drop a previously assigned customer back into the unserved pool, and in the over-provisioned reference scenario such swaps outweigh the few customers there are left to absorb. The final result is the best of the five orderings only, the initial greedy assignment itself is not kept as a candidate, so the pipeline does not fall back to it even when every ordering ends worse. Adding the greedy assignment as a sixth candidate would remove this failure mode.
